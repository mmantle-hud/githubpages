# Exercise: Database Design for a Hotel Finder App

The local tourist board want to make it easy for visitors to find hotels in the local area. They want to store data about different hotels: the name of the hotel, the star rating (1-5), the style of hotel (e.g. boutique, business, budget, luxury etc.), the price of a typical room, the distance from the city centre in kms, and the amenities on offer e.g. gym, restaurant, air conditioning etc.

1. Create a conceptual ERD that capture the key entities, their attributes and relationships in this description. 

2. Based on your conceptual ERD create a logical ERD. This should specify primary and foreign keys, data types, and junction tables if you have any many-to-many relationships. 

Based on the description, you may assume some additional attributes that aren't explicitly mentioned. However, don't be tempted to expand the scenario e.g. by considering bookings. Only model the entities described in the description. 

You can use any tool you like to create the ERDs. For this introductory exercise you could hand draw the ERD. Alternatively, you could use on online diagram editor such as https://www.drawio.com/ or https://dbdiagram.io/. 

In the notes we also looked at creating data dictionaries. To keep things simple and so the exercise doesn't take too long, don't worry about creating data dictionaries, or a physical data model.  


# Possible Solution: Database Design for a Hotel Finder App

## Conceptual ERD

**Conceptual ERD for the Hotel Finder App**

```mermaid
erDiagram
    accTitle: Conceptual model for the Hotel Finder App.
    accDescr: Conceptual model showing Hotel, Amenity and Style.
    Hotel }o--o{ Amenity : ""
    Hotel }o--|| "Style" : ""
    
    Hotel {
        _ hotelName
        _ price
        _ starRating
        _ distanceToCentreKms
    }

    Amenity {
        _ amentityName
        _ amentityDescription  
    }

    "Style" {
        _ styleName
    }
```

Your solution may not look exactly like this. You've probably named things a little differently. Here are the key things to check:-

- Your conceptual ERD only models real world entities. There shouldn't be any mention of primary keys, foreign keys etc.
- You've correctly identified that there is a many-to-many relationship between Hotel and Amenity. 
- You may not have modelling Style as a separate entity. You might have simply added a style attribute to the Hotel entity. This is fine. I'll explain why I've chosen to create a separate Style entity in the next reading task. 


## Logical ERD

**Logical ERD for the Hotel Finder App**

```mermaid
erDiagram
    accTitle: Logical model for the Hotel Finder App.
    accDescr: Logical model showing hotels, amenities and styles.
    hotels ||--o{ hotel_amenity : ""
    amenities ||--o{ hotel_amenity : ""
    hotels }o--|| styles : ""
    
    hotels {
        INT hotel_id PK
        TEXT hotel_name
        DECIMAL price
        INT star_rating
        DECIMAL distance_to_centre_kms
        INT style_id FK
    }
    styles{
        INT style_id PK
        TEXT style_name
    }
    amenities {
        INT amenity_id PK
        TEXT amenity_name
        TEXT amenity_description
        
    }
    hotel_amenity{
        INT hotel_id PK, FK
        INT amenity_id PK, FK
    }

```
Again, your answer may not be identical to this diagram. Here are the key things to check:
- The logical ERD should be consistent with the conceptual ERD. 
- Tables and columns have been named using a consistent naming convention.
- The diagram shows primary and foreign keys.
- The diagram shows suitable data types.
- There is a junction table for the many-to-many relationship.
