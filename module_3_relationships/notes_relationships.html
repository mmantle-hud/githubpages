Relationships

So far in the course we have worked with singe table databases. In anything other than really simple applications we are going to need more than a single table.

Imagine we are building a web application that will act as a travel guide for people wanting to go on a city break. They are going to use the website to help them choose which city to visit.

We'll need to store data about the different cities such as the name of the city, and it's average temperature. We might also want to store data about different countries where cities are located. For example, the name of the country and the currency used.

So I have two entities cities and countries.

We can show this visually on an ERD, an entity relationship diagram.

There is a relationship between these entities. A city is located in a country.

The arrow show the direction of the relationship and the label describes the relationship. So this states cities are located in countries.

We use verbs to describe relationships. For example a customer orders a product, a footballer scores a goal.

Cardinality

Another key thing about relationships is they have cardinality. What does this mean? It means how many of one thing can be related to the other.

Thinking about my travel guide example we need to ask the question

A city is located in how many countries?

The answer is one e.g. London is located in England, Paris is located in France, Delhi is located in India etc.

We also need to think about the relationship in the other direction

A country contains how many cities?

The answer is many e.g. England contains London, Manchester, Leeds etc. France contains Paris, Lyon, Marseille etc. India contains Mumbai, Dehli, Hyderabad and so on.

We say there is a one-to-many relationship between Country and City. One country can contain many cities, but a city is located in a single country. We write this as 1:M or 1:N.

There are lots of 1:M relationships between entities. For example league and football team. A league has many teams, but a team plays in a single league.

How do relationships relate to databases?

We want to store data about relationships as part of our database. In the travel guide example we want to record which country a city is located in.

cities

city_id city_name is_capital avg_temp_celsius country_id

In the cities table we show which country the city is located in by using the country's primary key value. We can see that Barcelona is in the country with the country_id of 2, it's in Spain.

We call this a foreign key.

A foreign key is a column in a database table that points to the primary key of another table.

We can also see that a single country e.g. Germany appears in the cities table many times.

We call the table on the one side of the relationship (in this example countries) the parent table, and we call the table on the many side of the relationship (cities) the child table.

How do we implement this?

The CREATE statement for countries is straightforward.

CREATE TABLE countries (
country_id INT GENERATED ALWAYS AS IDENTITY,
country_name TEXT NOT NULL,
total_population BIGINT NOT NULL,
currency_code CHAR(3) NOT NULL,
CONSTRAINT pk_countries PRIMARY KEY (country_id)
);

CHAR is used for a fixed length string. Currency codes are always three letters in length.

The SQL for creating the cities tables:

CREATE TABLE cities (
  city_id INT GENERATED ALWAYS AS IDENTITY,
  city_name TEXT NOT NULL,
  is_capital BOOLEAN DEFAULT false,
  avg_temp_celsius NUMERIC(3, 1) NOT NULL,
  country_id INT NOT NULL,
  CONSTRAINT pk_cities PRIMARY KEY (city_id),
  CONSTRAINT fk_cities_countries FOREIGN KEY (country_id) REFERENCES countries (country_id)
);

There are a couple of new data types we haven't seen before that are worth discussing. is_capital will store BOOLEAN value i.e. TRUE or FALSE. The DEFAULT keyword simply states if an INSERT statement doesn't specify a value PostgreSQL will use FALSE as a default. avg_temp_celsius uses the NUMERIC data type for fixed point numbers. The first argument, 3 specifies the total number of digits, the second argument, 1, specifies how many digits are allowed to the left of the decimal point, so this column will allow numbers such as 23.5, 12, -3.2, we use a single decimal place.

The important thing to focus on is the foreign key column, country_id. We declare country_id as a column, making sure we match the data type of the parent table.

We also add a constraint that states this is a foreign key. The constraint is given a name fk_cities_countries, specifies the foreign key column FOREIGN KEY (country_id), and the table and column it links to REFERENCES countries (country_id)

Again, the naming is important. Try and use a consistent clear naming for the constraint e.g.fk_child_table_parent_table.

Optionality

The diagram also show optionality. Optionality specifies if a relationship is optional or mandatory.

Next to the crow's foot there is an inner symbol, a circle. This indicates the relationship is optional for countries. A country can exist in the database without having any associated cities. For example, Canada is in the countries table, but no Canadian cities have been added yet.

The inner symbol on the countries side, also a short line (|) indicates this relationship is mandatory. A city must be associated with a country. We can't add a city unless we specify the country it is located in.

Referential Integrity

  • Foreign keys enforce referential integrity. This means when we set up a foreign key two constraints are created:
  1. Child tables can only use ids from the parent table.
  2. Can't delete rows from the parent table if they are being used by the child table.

Joins

Querying tables in a 1:M relationship involves using a join. JOIN is a command to combine rows from two tables based on a shared column.

SELECT 
cities.city_name, countries.country_name 
FROM cities
INNER JOIN countries ON cities.country_id = countries.country_id;
city_name country_name
Berlin Germany
Munich Germany
Hamburg Germany
Madrid Spain
Barcelona Spain
Tokyo Germany

See how the results show a column from the cities table and a column from the countries table. Specifically this is an INNER JOIN. For each city, we look for the matching country_id in the countries table and display the country's name. When specifying the columns we want to retrieve, we prefix the column name with the table name to make it clear which column we want to retrieve.

Filtering and Grouping using a Join

Last week we learnt about sorting, filtering and grouping. These ideas still apply when joining tables e.g. using WHERE

SELECT 
cities.city_name, countries.country_name, cities.avg_temp_celsius
FROM cities
INNER JOIN countries ON cities.country_id = countries.country_id
WHERE cities.avg_temp_celsius > 10
ORDER BY avg_temp_celsius DESC;
city_name country_name avg_temp_celsius
Barcelona Spain 18.2
Tokyo Germany 16.5
Madrid Spain 15.0
Berlin Germany 10.5

Or using a GROUP BY

SELECT 
countries.country_name, COUNT(cities.city_name) AS num_of_cities
FROM countries
INNER JOIN cities ON countries.country_id = cities.country_id
GROUP BY countries.country_name;
country_name num_of_cities
Spain 2
Germany 4

Note that Canada isn't included in the results. With INNER JOIN we only join where there is a match between the parent row and child rows. To display Canada and 0, we'd use a LEFT JOIN which we'll learn about in the coming weeks.

Many-to-Many relationships

The other key relationship we need to be aware of is a many-to-many relationship.

Imagine a music school. a conservatory. wants to keep track of it's students and the musical instruments they play.

Again I could show this visually

classDiagram 
   Musician --> Instrument : plays
   class Musician{
     given name
     family name
   }
   class Instrument{
     instrument name
   }

Now lets think about the cardinality

A musician can play how many instruments?

The answer is many e.g. If we think of a musician such as Prince. he could play guitar, keyboards, drums, bass etc.

And in the other direction

The answer is also many e.g.

An instrument can be played by how many musicians? For example, lots of musicians can play piano - Nina Simone, Stevie Wonder, Paul McCartney etc.

We say there is a many-to-many relationship between Musician and Instrument.

A musician can play many instruments, and an instrument can be played by many musicians.

The important thing here is we are talking about types of instrument - piano, violin, guitar etc. Not specific individual instances.

We write this as M:M or M:N.

Again many-to-many relationships are very common.

For example, in an ecommerce application

An order is made up of many products. A product can be part of many orders.

A students studies in many courses A course is studied by many students

Implementation in a database

How do we implement a many-to-many relationship in a database?

musician_id given_name family_name
1 Alex Mercer
2 Elena Rostova
3 Marcus Vance
4 Chloe Tanaka
5 Zubair Ali
instrument_id instrument_name
1 Violin
2 Drums
3 Flute
4 Keyboard

There isn't a parent child relationship so we can't simply add a foreign key column.

You might be tempted to add a foreign key column to store multiple id numbers

musician_id given_name family_name instrument_ids
1 Alex Mercer 2
2 Elena Rostova 1
3 Marcus Vance 2, 4
4 Chloe Tanaka 4
5 Zubair Ali 1, 2, 4

But this is a really bad idea, each field should store a single value, and we can't enforce referential integrity using this approach.

Instead, what we do is add an additional table. Each row in this table will store the id number of a musician and an instrument.

musician_id instrument_id
1 2
2 1
3 2
3 4
4 4
5 1
5 2
5 4

So there are two foreign key columns musician_id and instrument_id.

In this way we can link a musician to multiple instruments, and an instrument to multiple musicians.

So we can see that Marcus Vance plays Drums and Flutes.

We can also see that the Violin is played by Elena Rostova and Zubair Ali.

We call this table a bridging table, junction table, or a linking table.

The naming convention is to call it table1_table2 but use singular terms i.e. instrument_musician.

What is the primary key for this table?

This table uses a composite primary key, a combination of two columns, musician_id and instrument_id.

Although the same musician_id appears across multiple rows, and the same instrument_id appears across multiple rows. The combination of the two is unique. For example, there can only be one row with the 2,1 combination.

CREATE SQL

How do we create the junction table and set up the keys correctly?

CREATE TABLE musicians(
    musician_id INT GENERATED ALWAYS AS IDENTITY,
    given_name VARCHAR(255) NOT NULL,
    family_name VARCHAR(255) NULL,
    CONSTRAINT pk_musicians PRIMARY KEY (musician_id)
);
CREATE TABLE instruments(
    instrument_id INT GENERATED ALWAYS AS IDENTITY,
    instrument_name VARCHAR(255) NOT NULL,
    CONSTRAINT pk_instruments PRIMARY KEY (instrument_id)
);
CREATE TABLE musician_instrument(
    musician_id INT,
    instrument_id INT,
    CONSTRAINT pk_musician_instrument PRIMARY KEY (musician_id,instrument_id),
    CONSTRAINT fk_musician_instrument_musicians FOREIGN KEY (musician_id) REFERENCES musicians(musician_id) ON DELETE CASCADE,
    CONSTRAINT fk_musician_instrument_instruments FOREIGN KEY (instrument_id) REFERENCES instruments(instrument_id) ON DELETE CASCADE
);

The musicians and instruments tables don't show anything new.

The junction table has a composite primary key, so we list both columns under PRIMARY KEY. Both these columns are also foreign keys. We need a constraint for each.

Again we use ON DELETE CASCADE. If we remove a musician or instrument form the database, the associated records should be deleted.

Using Aliases

As our joins get more complex it is common practice to use table aliases e.g.

SELECT 
    m.given_name, 
    m.family_name,
    i.instrument_name
FROM musicians AS m
INNER JOIN musician_instrument AS mi ON m.musician_id = mi.musician_id
INNER JOIN instruments as i ON mi.instrument_id= i.instrument_id;

If we have very large databases with lots of tables that start with the same letter we might use the first few letter e.g. mus, ins.

Again we can use filtering and grouping. For example to find the names of all the musicians that play the violin.

SELECT

    m.family_name,
    i.instrument_name
FROM musicians AS m
INNER JOIN musician_instrument AS mi ON m.musician_id = mi.musician_id

SELECT 
    m.given_name, 
    m.family_name,
    COUNT(mi.instrument_id) AS num_instruments
FROM musicians AS m

SELECT

    m.family_name,

Language Codes

Using a surrogate key (like an auto-incrementing id) is a common industry standard, but for a global language table, the standard ISO language code (en, ja, fr) is actually the superior and more realistic choice.Here is why using a natural key like an ISO code makes more sense than a surrogate key in this specific scenario:1. It is a Globally Recognized Natural KeyA surrogate key is used when the natural data is messy, prone to typos, or changes over time (like human names or addresses).However, ISO 639-1 language codes are a rigid, unchanging international standard.en will always mean English.ja will always mean Japanese.These codes will never change or need updating, completely eliminating the risk of update anomalies.2. Cleaner, More Readable Foreign KeysIf you use a surrogate key, your movies table will look like this:movie_idtitlelanguage_id (FK)1Toy Story3A developer or student looking at this raw table has no idea what language 3 is without constantly writing an explicit JOIN statement.If you use the ISO code, the table remains incredibly clear and scannable, even without joining the parent table:movie_idtitlelanguage_code (FK)1Toy Storyen3. Better Query PerformanceBecause en or ja is already stored directly inside the movies table row, developers can filter movies by language (WHERE language_code = 'ja') instantly. The database does not need to perform a costly join operation to a lookup table just to check a basic 2-letter abbreviation.The Teaching Angle: A Perfect "Natural vs. Surrogate" LessonUsing the ISO code gives you a fantastic opportunity to teach your students that surrogate keys are not a silver bullet.You can explain to them that while surrogate keys are perfect for tracking changing business entities (like Employees, Camps, or Assignments), stable, international standards (like language codes, country codes like GB/US, or currency codes like GBP/USD) should be left as natural primary keys.
