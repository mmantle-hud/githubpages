# Many-to-Many Relationships
Previously we looked at the idea of a one-to-many relationship. Another key relationship we need to be familiar with is a many-to-many (M:M) relationship.

Consider designing a database for a music school. The school need to keep track of their students and the musical instruments they play. 

Again we can show this visually on an ERD.

 ```mermaid
classDiagram 
    Musician --> Instrument : plays
    class Musician{
      given name
      family name
    }
    class Instrument{
      instrument name
    }
```
Now let's consider the cardinality. A musician can play how many instruments? The answer is **many** e.g. If we think of a musician such as Prince. He could play guitar, keyboards, drums, bass etc.

And in the other direction, an instrument e.g. piano can be played by how many musicians. The answer is also **many** e.g. lots of musicians can play piano - Nina Simone, Stevie Wonder, Paul McCartney etc. 

We say there is a many-to-many relationship between Musician and Instrument. A musician can play **many** instruments, and an instrument can be played by **many** musicians. 

>The important thing here is we are talking about types of instrument - piano, violin, guitar etc. Not specific individual instances of a musical instrument. 

Again many-to-many relationships are very common. For example, in an ecommerce application, an order is made up of **many** products. A product can be part of **many** orders. In a university, a students studies **many** different courses. A course is studied by **many** students.

## M:M Relationships in Database Tables
How do we implement a many-to-many relationship in a database? 

**musicians**

| musician_id (PK) | given_name | family_name |
| :--- | :--- | :--- |
| 1 | Alex | Mercer |
| 2 | Elena | Kowalski |
| 3 | Marcus | Vance |
| 4 | Chloe | Tanaka |
| 5 | Zubair | Ali |

**instruments**

| instrument_id (PK) | instrument_name |
| :--- | :--- |
| 1 | Violin |
| 2 | Drums |
| 3 | Flute |
| 4 | Keyboard |

There isn't a parent-child relationship so we can't simply add a foreign key column. You might be tempted to add a foreign key column to store multiple ID numbers.

#### musicians

| musician_id (PK) | given_name | family_name |instrument_ids|
| :---------- | :--------- | :-----------|:-------------|
| 1           | Alex       | Mercer      |2             |
| 2           | Elena      | Kowalski    |1             |
| 3           | Marcus     | Vance       |2, 4          |
| 4           | Chloe      | Tanaka      |4             |
| 5           | Zubair     | Ali         |1, 2, 4       |

This would be a bad idea! Each field in a database table should store a single value. We can't enforce referential integrity using this approach. Instead, we create an additional table. Each row in this table will store the ID number of a musician and the ID number of an instrument. 

**musician_instrument**

| musician_id | instrument_id |
| :--- | :--- |
| 1 | 2 |
| 2 | 1 |
| 3 | 2 |
| 3 | 4 |
| 4 | 4 |
| 5 | 1 |
| 5 | 2 |
| 5 | 4 |

This table features two foreign key columns `musician_id` and `instrument_id`. In this way we can link a musician to multiple instruments, and an instrument to multiple musicians. So we can see that Marcus Vance (ID=3) plays Drums (ID=2) and Keyboard (ID=4). The relationship also works in the opposite direction. We can see that the Violin is played by Elena Kowlaski and Zubair Ali. 

We call this table a bridging table or **junction table**. The naming convention is to call it `table1_table2` but use singular terms i.e. `instrument_musician`.

What is the primary key for this table? This table uses a **composite primary key**. A composite primary key is a combination of two or more columns used together to uniquely identify a single row in a table. In this example it is a combination of two columns, `musician_id` and `instrument_id`. Although the same `musician_id` appears across multiple rows, and the same `instrument_id` appears across multiple rows, the combination of the two is unique. For example, there can only be one row with the (2,1) combination. 

## SQL `CREATE` for a Junction Table
How do we create the junction table and set up the keys correctly?

```sql
CREATE TABLE musicians(
    musician_id INT GENERATED ALWAYS AS IDENTITY,
    given_name VARCHAR(255) NOT NULL,
    family_name VARCHAR(255) NULL,
    CONSTRAINT pk_musicians PRIMARY KEY (musician_id)
);

CREATE TABLE instruments(
    instrument_id INT GENERATED ALWAYS AS IDENTITY,
    instrument_name VARCHAR(255) NOT NULL,
    CONSTRAINT pk_instruments PRIMARY KEY (instrument_id)
);

CREATE TABLE musician_instrument(
    musician_id INT,
    instrument_id INT,
    CONSTRAINT pk_musician_instrument PRIMARY KEY (musician_id,instrument_id),
    CONSTRAINT fk_musician_instrument_musicians FOREIGN KEY (musician_id) REFERENCES musicians(musician_id) ON DELETE CASCADE,
    CONSTRAINT fk_musician_instrument_instruments FOREIGN KEY (instrument_id) REFERENCES instruments(instrument_id) ON DELETE CASCADE
);
```
The `musicians` and `instruments` tables don't show anything we haven't seen previously.

The junction table has a composite primary key, so we specify a `PRIMARY KEY` constraint that features both columns.
Both these columns are also foreign keys. Therefore, we add a foreign key constraint for each of these columns. 

`ON DELETE CASCADE` means if a row in the parent table is deleted any linked row in the child table is also deleted. This will keep our database neat and tidy. Whenever we delete a musician or instrument, the associated rows in the junction table will be deleted automatically. 

Why didn't we use `ON DELETE CASCADE` for the cities and countries example? If we did, we would lose valuable data about the cities when we deleted a country. In the musicians and instruments example, the row only has meaning if both the musician and instrument exist.

## Querying a Junction Table
We'll break this down into steps

To start with we'll show joining the `musicians` table to the `musician_instrument` table

```sql
SELECT
    *
FROM
    musicians AS m
    INNER JOIN musician_instrument AS mi ON m.musician_id = mi.musician_id;
```

| musician_id | given_name | family_name | musician_id (1) | instrument_id |
|-------------|------------|-------------|-----------------|---------------|
| 1           | Alex       | Mercer      | 1               | 1             |
| 2           | Elena      | Kowalski    | 2               | 2             |
| 3           | Marcus     | Vance       | 3               | 3             |
| 3           | Marcus     | Vance       | 3               | 4             |
| 4           | Chloe      | Tanaka      | 4               | 4             |

We can then extend this to join all three tables:-

```sql
SELECT
    *
FROM
    musicians AS m
    INNER JOIN musician_instrument AS mi ON m.musician_id = mi.musician_id
    INNER JOIN instruments AS i ON mi.instrument_id = i.instrument_id;

```

|-------------|------------|-------------|-----------------|---------------|-------------------|-----------------|

| 2           | Elena      | Kowalski    | 2               | 2             | 2                 | Drums           |

At this point some people get confused. As we increase the complexity and join more tables, things can get confusing. My advice is to:
- Use 'select all' using the asterisk until you know the query works. Then you can fully see what is being joined.  Once you know the query works, you can choose the specific columns to display the in the resultset. 
- Try and build the join up step by step just like the example above. First, join two tables, then join three tables and so on. 

## Filtering and Grouping
Again we can use filtering and grouping. For example, to find the names of all the musicians that play the violin.

```sql
SELECT 
    m.given_name, 
    m.family_name,
    i.instrument_name
FROM musicians AS m
INNER JOIN musician_instrument AS mi ON m.musician_id = mi.musician_id
INNER JOIN instruments as i ON mi.instrument_id= i.instrument_id
WHERE i.instrument_name='Violin';
```

| given_name | family_name | instrument_name |
| :--- | :--- | :--- |
| Alex | Mercer | Violin |
| Zubair | Ullah | Violin |

We can use `GROUP BY`. For example, to get how many people play each instrument:-

```sql
SELECT 
    m.given_name, 
    m.family_name,
    COUNT(mi.instrument_id) AS num_instruments
FROM musicians AS m
INNER JOIN musician_instrument AS mi ON m.musician_id = mi.musician_id
GROUP BY m.given_name, m.family_name;
```

| given_name | family_name | num_instruments |
| :--- | :--- | :--- |
| Zubair | Ullah | 3 |
| Alex | Mercer | 1 |
| Marcus | Vance | 2 |
| Elena | Kowalski| 1 |
| Chloe | Tanaka | 1 |

Note, that we only need to join to the junction table, we don't need any data from the `instruments` table. 

We can also use `GROUP BY` for presentation purposes. This example uses string aggregation to output the instruments for each person in a single row. 

```sql
SELECT 
    m.given_name, 
    m.family_name, 
    STRING_AGG(i.instrument_name, ', ') AS instruments
FROM musicians m
INNER JOIN musician_instrument mi ON m.musician_id = mi.musician_id
INNER JOIN instruments i ON mi.instrument_id = i.instrument_id
GROUP BY m.musician_id, m.given_name, m.family_name;
```

| given_name | family_name | instruments |
| :--- | :--- | :--- |
| Chloe | Tanaka | Keyboard |
| Elena | Kowalski | Drums |
| Marcus | Vance | Flute, Keyboard |
| Alex | Mercer | Violin |
| Zubair | Ullah | Violin, Drums, Keyboard |
