# One-to-One Relationships and Self Relationships
One-to-one and self relationships are less common than one-to-many or many-to-many, but we should still be aware of them. 

## One-to-One Relationships
A government might want to record details of its citizens and key documents such as passports or driving licenses. 

<pre class="mermaid">
classDiagram 
    direction LR
    Person --> Passport : owns
    class Person{
      given name
      family name
      date of birth
    }
    class Passport{
      passport number
      date of issue
    }
</pre>

What's the cardinality for this 'owns' relationship? A person can own how many passports?

It depends what we are modelling. 
- Many people have dual citizenship, they can legally a hold different passports issued by different countries. However, if we are designing a database for a specific country they probably don't need to keep track of passports issued by other countries; they would only be concerned with the passports they have issued. 
- I am also assuming that we aren't keeping track of expired passports or lost passports, we are only concerned with a person's current, active passport. 

Based on these assumptions, a person owns **one** passport. 

The opposite direction is easier. A passport is owned by how many people? The answer is always **one**. 

We say there is a **one-to-one** (1:1) relationship between Person and Passport. A person can own **one** passport, and a passport can be owned by **one** person. 

### 1:1 Relationships in Database Tables
How do we implement a one-to-one relationship in a database? 

```sql
CREATE TABLE people (
    person_id INT GENERATED ALWAYS AS IDENTITY,
    given_name VARCHAR(255) NOT NULL,
    family_name VARCHAR(255) NULL,
    date_of_birth DATE NOT NULL,
    CONSTRAINT pk_people PRIMARY KEY (person_id)
);

CREATE TABLE passports (
    passport_number CHAR(9),
    date_of_issue DATE NOT NULL,
    person_id INT NOT NULL UNIQUE,
    CONSTRAINT pk_passports PRIMARY KEY (passport_number),
    CONSTRAINT fk_passports_people FOREIGN KEY (person_id) REFERENCES people(person_id) ON DELETE CASCADE
);
```
In a one-to-one relationship we can put the foreign key in either table. I have chosen to put it in `passports`. A person can exist without a passport, but the opposite isn't true. `ON DELETE CASCADE` is used so that if a person is removed from the database, the passport will also be deleted. 

This is very similar to a one-to-many relationship. To make this a one-to-one relationship and ensure a person can't have multiple passports we add a `UNIQUE` constraint to the `person_id` column. 

Let's look at some example tables and a query.

**people**

| person_id (PK) | given_name | family_name | date_of_birth | 
|-----------|------------|-------------|---------------| 
| 1         | Sarah      | Jones       | 1992-11-23    | 
| 2         | Aisha      | Kahn        | 1994-03-14    | 
| 3         | Kwame      | Mensah      | 1997-05-19    | 


**passports**

| passport_number (PK) | date_of_issue | person_id (FK)| 
|-----------------|---------------|-----------| 
| 503214567       | 2019-06-12    | 1         | 
| 508765432       | 2022-10-25    | 2         | 
| 501472583       | 2025-02-18    | 3         | 
 

```sql
SELECT
    CONCAT(p.given_name, ' ', p.family_name) AS full_name,
    pa.passport_number
FROM
    people AS p
    INNER JOIN passports AS pa ON p.person_id = pa.person_id;
```

| full_name    | passport_number | 
|--------------|-----------------| 
| Sarah Jones  | 503214567       | 
| Aisha Kahn   | 508765432       | 
| Kwame Mensah | 501472583       | 

This should all make sense, the `INNER JOIN` has exactly the same structure as a one-to-many relationship. 

## Self Relationships
The most common example of a self-relationship is an employee management database where we need to store the details of employees and their line manager. Managers are also employees so we have a self relationship.

<pre class="mermaid">
classDiagram 
    Employee --> Employee : "is managed by"
    class Employee{
      given name
      family name
      date of birth
    }
</pre>
>
What is the cardinality of this relationship? An employee is managed by **one** manager. A manager manages **many** employees. There is a one-to-many relationship between manager and employee. 

To implement this in SQL.

```sql
CREATE TABLE employees (
    employee_id INT GENERATED ALWAYS AS IDENTITY,
    given_name VARCHAR(255) NOT NULL,
    family_name VARCHAR(255) NULL,
    manager_id INT NULL,
    CONSTRAINT pk_employees PRIMARY KEY (employee_id),
    CONSTRAINT fk_employee_manager FOREIGN KEY (manager_id) 
        REFERENCES employees(employee_id) ON DELETE SET NULL
);
```

**employees**

| employee_id (PK) | given_name | family_name | manager_id (FK) | 
|-------------|------------|-------------|------------| 
| 1           | Kwame      | Mensah      | NULL       | 
| 2           | Sara       | Jones       | 1          | 
| 3           | Usman      | Hussain     | 1          | 
| 4           | Tom        | Smith       | 2          | 

`manager_id` is our foreign key column. It references an `employee_id` in the same table. We can see that Tom Smith is managed by Sara Jones. 

We specify this foreign key is nullable. Kwame Mensah is the CEO, he isn't managed by anybody so we make his `manager_id` NULL. We also add `ON DELETE SET NULL`. If a manager leaves the company we don't want to delete all the people they manage. Instead, this will set their `manager_id` value to NULL ready for them to be assigned a new manager. 

Again, we can query this table using an `INNER JOIN`

```sql
SELECT
    CONCAT(e.given_name, ' ', e.family_name) AS employee,
    CONCAT(m.given_name, ' ', m.family_name) AS manager
FROM
    employees AS e
    INNER JOIN employees AS m ON e.manager_id = m.employee_id;
```

| employee      | manager      | 
|---------------|--------------| 
| Sara Jones    | Kwame Mensah | 
| Usman Hussain | Kwame Mensah | 
| Tom Smith     | Sara Jones   |
