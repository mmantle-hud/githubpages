# ACID

ACID is a set of four guarantees that relational databases make about transactions. 

In the last set of reading we described a transaction as being a block of multiple statements, the following principles also apply when executing a single SQL statement. 

## A: Atomicity

Atomicity means that all SQL statements in a transaction are treated as an all-or-nothing package. If any statement fails or the system crashes part-way through, the transaction can be rolled back and none of its changes are saved.

Using a transaction to transfer money between bank accounts, like we saw in the last reading, is a good example. 

If the money is taken from Alice's account but the system crashes before it reaches Bob's account, atomicity means the whole transaction is undone. The £100 goes back to Alice.

## C: Consistency

Consistency means a transaction takes the database from one **valid state** to another. Any rules defined on the data (primary keys, foreign keys, `NOT NULL`, `CHECK`, `UNIQUE` etc.) must still hold after the transaction has completed. If an attempted transaction breaks a rule, it is rejected.

For example, in the assessment database, if we tried to update the student score to be greater than 100 e.g. 101, a  `CHECK` constraint forbids it.

Importantly, a database can only enforce rules we've defined. If we don't add a `CHECK` constraint for the student score, invalid data can still be entered.  

## I: Isolation

Isolation means users don't interfere with each other.

When many transactions run at the same time, each behaves **as if it were running alone**. Changes made inside a transaction are not visible to other users until it is committed.

In the ticket booking example from the last reading, User B can still see seat 23E as available while User A's transaction is in progress, because A's changes aren't committed yet. 

Isolation stops users seeing each other's half-finished work, but it doesn't automatically stop two users making the same decision from the same information. That is why we also had to lock the row with `FOR UPDATE`, so User B had to wait until User A had finished.


## D: Durability 

When a transaction is committed, it is complete.

Once a transaction has been **committed**, it stays committed, even if the power fails or the server crashes immediately afterwards. The database achieves this by writing changes to disk before confirming success.

If Alice gets a "payment successful" message. Even if the server crashes a second later, the payment is still there when it restarts.
