# Indexes
An **index** in a relational database is a separate data structure designed to speed up selecting rows from a table.

Let's look at an example to understand what this means. 

Here's the `students` table we have looked at previously. 

| student_id (PK) | given_name | family_name | degree_id (FK) | 
|-----------------|------------|-------------|----------------| 
| 1               | Elizabeth  | Fong        | 1              |  
| 2               | Donald     | Chamberlin  | 2              | 
| 3               | Michael    | Stonebraker | 2              | 
| 4               | Tracy      | Chou        | 3              | 
| 5               | Radia      | Perlman     | 3              | 
| 6               | Tim        | Berners-Lee | 4              | 
| 7               | Brendan    | Eich        | 4              | 
| 8               | Håkon Wium | Lie         | 6              | 
| 9               | Jen        | Simmons     | 3              | 

We run a query on this table.

```sql
SELECT *
FROM students
WHERE family_name = 'Simmons';
```
PostgreSQL will do a full **table scan**. It will look at each row in turn, if the `family_name` column is equal to 'Simmons' the row will be added to the result set. 

This will run very fast for the table above as there are only nine students. What if the table contains hundreds of thousands of students? A full table scan is going to take much longer. 

We can use an index to speed up finding rows that match our query. 

## B-trees
RDBMS often use a Balanced tree (B-tree) index to speed up queries. For example, if we created a B-tree index on the `family_name` column. The database would create the following structure:

At the leaf nodes i.e. where we store the family names, the RDBMS also stores pointers to full records. 

Now, instead of doing a full table scan, the RDBMS would do the following:
- **Root**. Is 'Simmons' between A and M? No.
- **Root**. Is 'Simmons' between N and Z? Yes, move on to N-Z.
- **N-Z**. Is 'Simmons' between N and R? No.
- **N-Z**. Is 'Simmons' between S and Z? Yes, move on to S-Z
- **S-Z**. Does 'Simmons' match? Yes, add to result set.
- **S-Z**. Does 'Stonebraker' match? No.

We can find the correct results in fewer steps, speeding up our query. 

RDBMS are very effective at creating B-trees. They will create balanced splits and if needed split using the second or third letter.

If we had a million rows, we may have more splits and more leaf nodes, but the query would still run significantly faster than doing a full table scan. 

It isn't only text data we can index, we can index using numbers and dates. 

RDBMS also support composite indexes (e.g. (family_name, given_name)), which can speed up queries that filter on multiple columns e.g. using `AND` conditions in a `WHERE` clause.

## Disadvantages of Indexes
There are two main disadvantages of creating indexes:
1. Extra disk space is needed to store the index.
2. Whenever we run `INSERT`,`UPDATE` or `DELETE` we have to re-arrange the index. 

## When Should We Create an Index
All primary key columns are indexed automatically. 

We should also index foreign keys. This prevents full table scans during joins. 

Other occasions to consider indexes:
- When a column is regularly the subject of a `WHERE` clause
- When a column is regularly used in `ORDER BY` or `GROUP BY`
- When there is high cardinality (lots of different values) e.g. email addresses. 

When to avoid indexes:
- Small tables. What do we mean by small? It depends on the table structure, data types etc. But we usually don't need to consider indexes until we have 1000s of rows. 
- When there is low cardinality e.g. a Boolean value for recording if a student has submitted an assessment. 
- Tables that experience frequent inserts and/or updates.

Instead of setting up all our indexes when we first create our tables, often it is a good idea to see how users are using our database, and what type of queries they run. This will help us identify which columns we need to index.

It is also worth remembering that indexes speed up lookups, but they don't help queries that scan the entire table anyway (e.g. `SELECT COUNT(*) FROM students`).

## How to Create Indexes
Indexes are created using `CREATE INDEX`. PostgreSQL will take care of creating the actual index. 
```sql
-- Create the table structure
CREATE TABLE students (
    student_id INT GENERATED ALWAYS AS IDENTITY,
    given_name VARCHAR(255) NOT NULL,
    family_name VARCHAR(255) NULL,
    degree_id INT NOT NULL,
    CONSTRAINT pk_students PRIMARY KEY (student_id),
    CONSTRAINT fk_students_degrees FOREIGN KEY (degree_id) REFERENCES degrees(degree_id)
);
-- Keep the custom indexes next to the CREATE TABLE statement
-- Index the FK
CREATE INDEX idx_students_degree_id ON students(degree_id);
-- Index the family_name column
CREATE INDEX idx_students_family_name ON students(family_name);
```
